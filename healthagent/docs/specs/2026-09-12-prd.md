# Product Requirements Document — Event-Driven Health Intelligence Platform

**Date:** 2026-09-12
**Status:** Draft for review
**Owner:** Agent/Backend team

---

## 1. Summary

A health intelligence platform that correlates **life events** (eating, drinking
alcohol, smoking, exercise, therapy sessions) with **continuous physiological
signals** from wearables, then explains — in plain language — what those events
are doing to the user's body.

Existing wearables (Oura, WHOOP, Ultrahuman) tell you *what your body did*. They
do not reliably tell you *what caused it*, because they do not know what you were
doing. This platform closes that loop by capturing the event and the
physiological response together, then reasoning over both alongside the user's
genetics, lab reports, therapy history, and environment.

## 2. Problem Statement

A user who drinks alcohol on Tuesday sees a poor recovery score on Wednesday.
Current products show the score. They do not say:

> "Your resting heart rate rose 14 bpm and HRV dropped 31% after two drinks —
> a stronger response than your baseline, consistent with your slow-metabolizer
> genotype. Your last three sauna sessions each shortened this recovery by
> roughly half a day."

Producing that statement requires four things no single product currently
combines:

1. Knowing an event occurred, and when it started and ended.
2. Continuous physiological data around that window.
3. Static context — genetics, allergies, lab results, conditions.
4. Environmental context — temperature, humidity, UV, air quality, location.

## 3. Goals

### 3.1 Primary Goals

| # | Goal | Success measure |
|---|---|---|
| G1 | Capture events with start/end windows | 3 input methods: button, voice, auto-detection |
| G2 | Correlate events with physiological response | Per-event before/during/after deltas vs personal baseline |
| G3 | Deliver proactive, mid-event guidance | Alert delivered while event is still in progress |
| G4 | Automatically detect events without user input | ≥4 event types auto-detected at acceptable precision |
| G5 | Answer freeform health questions conversationally | Chat grounded in that user's own data |
| G6 | Produce periodic summaries | Daily digest and weekly report |

### 3.2 Non-Goals (explicitly out of scope)

- **Medical diagnosis.** The system describes and correlates; it never diagnoses.
- **Medication or dosage advice.** Hard-blocked at the guardrail layer.
- **Hardware.** We consume third-party wearable data; we do not build devices.
- **Mobile application.** Owned by a separate team. This project is backend +
  agent only.
- **Food recognition / macro estimation.** Not achievable with the available
  sensor set.

## 4. Users

**Primary:** health-optimising individuals already wearing a ring or band who
actively experiment with inputs (diet, alcohol, therapy protocols) and want to
understand causal effects on their own physiology.

**Secondary:** users undergoing structured therapy protocols (sauna, cold
exposure, red light, hyperbaric) who need before/after evidence that a protocol
is working.

## 5. Scope of This Project

This repository covers **backend and agent only**.

```
   OWNED BY OTHERS                    THIS PROJECT
   ┌──────────────────┐              ┌────────────────────────────┐
   │  Mobile app (UI) │              │  Ingest gateway            │
   │  Auth screens    │──Supabase──▶ │  Detector service          │
   │  Report upload   │   (shared    │  Analytics layer           │
   │  Device BLE sync │    data      │  Agent orchestrator        │
   └──────────────────┘    plane)    │  Scheduler + workers       │
                                     └────────────────────────────┘
```

**Integration contract:** the mobile team and the agent team communicate *only*
through Supabase tables. The mobile app never calls the agent directly and has
no knowledge that it exists. The agent is deployed in an isolated environment
whose address is not published to frontend clients.

## 7. Non-Functional Requirements

### 7.1 Performance

| ID | Requirement | Target |
|---|---|---|
| NFR-1.1 | Webhook ingest acknowledgement | < 100 ms (p95) |
| NFR-1.2 | Event → first agent output | < 30 s (p95) |
| NFR-1.3 | Detection latency (auto-detected events) | < 2 min |
| NFR-1.4 | Deterministic REST endpoints | < 300 ms (p95) |
| NFR-1.5 | Chat first token | < 2 s (p95) |

### 7.2 Scale

- Design target: **10,000 active users**, ~5 events/user/day.
- Telemetry: assume worst case 1 Hz × 8 channels/user; validate against actual
  device capability before sizing (most consumer rings emit 1–5 min aggregates,
  so real volume is expected to be materially lower).
- Workers scale horizontally; no worker holds user state between jobs.

### 7.3 Security and Privacy

| ID | Requirement |
|---|---|
| NFR-3.1 | All webhook calls authenticated via shared secret; unverified requests rejected before any field is trusted |
| NFR-3.2 | Agent uses service-role credentials; **application code is solely responsible for tenant scoping** |
| NFR-3.3 | Every data access scoped by `user_id` through a single audited context loader |
| NFR-3.4 | Agent service not publicly addressable from frontend clients |
| NFR-3.5 | Long-term memory namespaced per user; cross-user retrieval structurally impossible |
| NFR-3.6 | Health data encrypted at rest and in transit |
| NFR-3.7 | Prompt-injection sanitisation on all user-supplied text and uploaded documents |
| NFR-3.8 | Full audit log of agent data access, keyed by `user_id` and `session_id` |

### 7.4 Safety

| ID | Requirement |
|---|---|
| NFR-4.1 | Deterministic post-LLM guardrail blocks diagnosis, medication, and dosage advice |
| NFR-4.2 | Clinically dangerous values trigger mandatory escalation language |
| NFR-4.3 | Alert *decisions* are rule-based and unit-tested; the LLM controls wording only |
| NFR-4.4 | Safety-critical facts (allergies, conditions, medications) fetched deterministically, never via similarity search |

### 7.5 Cost Control

| ID | Requirement |
|---|---|
| NFR-5.1 | Per-session caps on tokens, tool calls, and wall-clock time |
| NFR-5.2 | No LLM inference in the continuous telemetry path |
| NFR-5.3 | Deterministic computation preferred over LLM wherever a correct answer exists |
| NFR-5.4 | Candidate (unconfirmed) events processed in a reduced-cost mode |

## 8. Event Taxonomy

Events are triaged by whether the available sensors can plausibly detect them.
This directly governs where detector effort is spent.

### Tier A — reliably detectable (detector targets)

| Event | Signature |
|---|---|
| Sleep | Standard wearable capability |
| Exercise / walking / running / dancing | Distinct motion signatures |
| Alcohol | Elevated resting HR, suppressed HRV, raised skin temp, multi-hour persistence |
| Sauna / heat therapy | Sharp skin temp rise + HR elevation with near-zero motion |
| Cold plunge | Sharp temp drop, HR spike then pronounced drop |

### Tier B — partially detectable

| Event | Note |
|---|---|
| Eating | Real postprandial HR rise (~10–15 bpm); wrist devices add hand-to-mouth motion. Weaker on rings. |
| Caffeine | Directionally similar to alcohol but subtler and shorter |

### Tier C — not detectable with this sensor set (manual/voice only)

| Event | Why |
|---|---|
| Smoking | Short, subtle, no distinctive motion |
| Red light therapy | Physiologically gentle by design — little to observe |
| Specific foods | Requires CGM or imaging; out of reach |
| Hyperbaric | Possible SpO2 signal, unvalidated |

> **Design consequence:** Tier C events remain fully supported as *manual* inputs
> and are valuable context for the agent. They are simply not detector targets.
> The agent reasons over all events; the detector only auto-captures Tier A.

## 9. Phasing

### Phase 1 — Manual Foundation
Event capture by button; telemetry ingestion and feature computation; baselines;
analytics layer; agent triggered on event with prediction written back; Realtime
delivery to app. **Also: testing team generates 100–200 labelled events** across
Tier A/B types to seed the detector training set.

### Phase 2 — Intelligence Layer
Voice event logging; document extraction; environment enrichment; genetics
integration; chat; scheduled digests and reports; threshold alerts; human-in-the-loop.

### Phase 3 — Automation
Rule-based detector live in shadow mode; candidate events with confirmation UX;
ML classifier trained on accumulated labels; continuous retraining loop.

## 10. Key Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Insufficient per-class training data (~13/type at 200 events across 15 types) | Detector fails to generalise | Concentrate labelling on 4–6 Tier A events; target 30–50+ instances each across many people |
| Model evaluated with window-level splits | Inflated accuracy, production collapse | **Split by user.** Hold out entire people from training |
| Class imbalance (>95% "nothing happening") | Accuracy metric is meaningless | Track precision/recall per class; mine hard negatives |
| Label noise at event boundaries | Model learns wrong boundaries | Exclude 1–2 min buffer at each boundary; support retroactive start |
| False positives erode trust | Users disable the feature | Start with deliberately high confidence thresholds; lower only as proven |
| Detector feedback loop is self-biased | Model calcifies around blind spots | Periodically sample random unflagged windows for user labelling |
| Training/serving skew | Silent model degradation | One shared feature module used by both detector and training job |
| Cross-tenant data leak | Severe — health data | Single audited context loader; tools cannot accept arbitrary user ids |
| Unbounded agent loops | Runaway cost | Hard per-session budget caps |
| Device capability assumptions wrong | Sizing and detection design invalidated | **Resolve before implementation** (see §11) |

## 11. Open Questions

1. **Which wearable(s)?** Exact sensor channels, sampling rates, and API access
   must be confirmed — this determines detector feasibility and storage sizing.
2. **Which 4–6 events are the detector's initial targets?**
3. Which therapy machines expose integrable data, and by what protocol?
4. What genetics source — consumer upload (23andMe export), clinical panel, or
   self-reported family history?
5. Regulatory posture: wellness product positioning vs. any regulated claim.
6. Data retention policy for raw telemetry and derived features.
